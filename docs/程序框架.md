# 程序框架与讲解顺序

## 分层与依赖

```text
main.c（组合入口：参数、初始化、循环、释放）
  ├─ platform.h → platform.c → Linux framebuffer/evdev 或 Win32 预览
  │    └─ calibrate.c（五点标定向导，画在 app->screen 上，不进入页面调度）
  │         └─ touchcal.h → touch_cal.c（纯整数拟合，无设备、无字库）
  └─ terminal.h → System.c（App 状态、事件分发、页面调度）
       ├─ MainScreenSystem.c（时钟与入口）
       ├─ AlbumSystem.c（目录扫描、缩略图、照片切换）
       ├─ WhiteboardSystem.c（笔触、画线、保存）
       ├─ GamesMenuSystem.c（四个游戏入口卡片）
       ├─ GameSystem.c → game.h → game.c（2048 纯规则）
       └─ GomokuSystem.c / ToeSystem.c / ChessSystem.c
            → boardgames.h → boardgames.c（五子棋、井字棋、象棋纯规则）
所有页面 → display.h → lcd.c / file_manager.c / print.c
print.c → 上游 truetype.c → res/simfang.ttf
```

`.c` 在 src，`.h` 在 inc；res 只存资源。lib 用于库说明；`upstream_font` 静态库由构建生成，不携带旧项目架构不明的二进制库。CMake 的 `terminal_core` 不包含设备平台实现，测试与实际程序共用它。项目是课程演示规模，不额外套用 RTOS、HAL 或复杂插件框架。

标定被拆成三层，是为了让它既能上板又能上桌：`touch_cal.c` 只做整数运算（每轴三个锚点、两段直线、按段外推到屏幕边缘、偏差判定），`calibrate.c` 负责画九个靶心、收九次点击、写文件，`platform.c` 只提供"当前原始值"和"换上实测锚点"两个动作。`tests/test_touch_cal.c` 因此不需要屏幕、不需要字库、不需要触摸设备，也能证明"中间下陷的面板被两段映射拉回原像素，而一条直线会偏 23 像素"。

## 状态与事件

App 拥有屏幕、画布、游戏图片、相册缓存和四副棋盘状态。Page 有 LOGIN、REGISTER、HOME、ALBUM、PHOTO、GAMES、2048、GOMOKU、TOE、CHESS、BOARD 十一个值；照片大图是相册模块的子页面，主页只显示三个入口，第二张卡片进入小游戏列表，再由列表进入单个游戏。

返回键按层级回退：棋局页面回到小游戏列表，列表回到主界面；相册、照片和画板直接回主界面。四副棋盘存在 App 里而不是页面里，所以离开再回来棋局不会被清空，只有页面右上角的 `重新开始` 会重置。

Linux 设备层将原始坐标按内核轴范围映射到 800×480，在 SYN_REPORT 边界形成 DOWN、MOVE、UP；检测到 SYN_DROPPED 时发 CANCEL。当前按单指交互设计，多点触控只取主触点，不提供缩放手势。这个"轴范围"默认取内核声明的；`data/touch.cal` 里的实测记录只有在与声明范围接近时才覆盖它（跨度差超过 1/7 或起点差超过 1/10 视为坏记录并忽略），因为本机实测证明声明范围就是准的，而只在下半屏取点的旧记录反而把上沿几行推低了一行。原始值经 `app_note_raw` 记进核心层，登录页把它和按下点、抬起点并排显示，并把落点画成红十字，于是"这个键点不动"变成一组可读的数字。

System 保存按下位置，只有按下和松开均在按钮内才激活，避免拖出误触。CANCEL 清除按下和绘画状态。画板从画布内按下才绘制，离开画布停止连线。游戏在棋盘内起始且横向或纵向位移超过 32 像素时判断滑动方向。

## 一次主循环

1. app_tick 检查秒数，只在主界面需要时标记 dirty。
2. 若 dirty，app_render 在内存画布绘制当前页面，platform_present 提交设备。
3. platform_poll 最多等待 16 ms 获取输入；设备读失败返回错误退出。
4. app_event 分发到当前页面，状态变化后设置 dirty。
5. 退出时先关闭平台，再释放图像和字体。

这不是 60 FPS 的性能承诺。设备绘制和 BMP 读写在主线程执行，实际响应时间取决于开发板；未进行板上帧率或延迟测量。

## 三条核心链路

画板保存：board_event → save_drawing → image_save → data/drawings/*.bmp。相册入口：album_scan → 扫描作品与内置照片 → 每页 6 张缩略图 → 点击后 load_photo。两个模块通过文件目录联动，无需互相修改内部列表。

2048 移动：game_event → game_move → game_slide → 挤压非零格 → 相邻相同数合并一次 → 回填零格 → 有变化才生成新格 → 判断胜负 → game_render。`game_slide` 不生成随机格，便于验证合并规则。

棋类落子：页面事件把屏幕坐标换算成棋盘下标（五子棋 25px 一格、井字棋 112px 一格、象棋 37px 一格，都按就近吸附），调用 boardgames.c 的 gomoku_place / toe_place / chess_move 改变局面，再在同一个事件里调用 gomoku_ai / toe_ai 让电脑应手。规则层不知道像素，也不知道 draw_*，因此 tests/test_boards.c 只链接 boardgames.c 就能验证连子判定和走子规则。

显示链路：页面绘制到 RGB 内存图像 → Linux 根据实际 RGB bitfield、line_length 和可视偏移写 framebuffer；Windows 用相同像素送到窗口。测试演示直接保存这块内存，避免另外制作一套演示界面。

## 源码讲解定位

| 顺序 | 打开文件 | 要讲清楚的内容 |
| --- | --- | --- |
| 1 | CMakeLists.txt、Makefile、inc/terminal.h | 源码分层、目标组成、App/Page/Event |
| 2 | src/main.c、src/System.c | 初始化、单循环、事件分发和资源释放 |
| 3 | src/system/platform.c | Linux 设备和 Windows 预览是两个实际实现 |
| 4 | src/system/touch_cal.c、calibrate.c | 为什么一个直线映射不够（实测中部偏 23 像素）；九个靶心怎么给每轴三个锚点、两段直线怎么接上不外扩 |
| 5 | src/WhiteboardSystem.c、AlbumSystem.c | 保存到目录，再进入相册扫描 |
| 6 | src/game.c、GameSystem.c | 合并和得分属于规则，按钮与绘制属于界面 |
| 7 | inc/boardgames.h、src/boardgames.c | 同一套规则接口服务三个棋种；将帅照面用"落子—判定—回退"实现 |
| 8 | tests/test_touch_cal.c、tests/test_boards.c、tests/test_terminal.c | 规则测试、BMP 边界和页面联动；区别于板上验收 |

## 检查边界

`tools/verify_project.py` 检查实现/头文件归属、核心文件不引用 Win32/Linux 设备头、纯规则不引用界面头（棋类与标定各有一组）、必要构建与资源。编译的告警视为错误。检查结果能证明这些机械约束，不能自动证明全部架构合理性；文件所有权、界面体验与设备时序仍需人工检查。
